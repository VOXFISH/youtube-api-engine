# RiceCon 사용법과 구현 명세

작성일: 2026-11-16 · 대상: Windows x64 · UI: Dear ImGui

`RiceCon.exe`는 Rice 게임 빌드를 받아 YouTube 방송 슬롯과 게임 인스턴스를 관리하는 별도 앱이다. `Rice.exe`는 편집기이며 `RicePlayer.exe`는 플레이어다. 완성 게임은 내보낸 게임 실행 파일을 열어 바로 시작한다.

## 실행과 빌드

Rice에서 게임을 내보낸 후 `RiceCon.exe`를 실행한다. **+ 항목 추가 → 실행 파일 선택**에서 내보낸 게임의 `.exe`를 선택하고 **추가**, 목록의 **재생**을 누른다. 게임 실행 파일을 RiceCon에 끌어 놓거나 다음처럼 명령줄로 전달해도 목록에 등록된다.

```powershell
.\RiceCon.exe ".\Builds\My Game.exe"

# 기본 사용자 설정과 별도로 목록을 보관할 때
.\RiceCon.exe --config "$env:TEMP\controller-demo\controller.json"

# 창을 숨긴 상태에서 ImGui 120프레임을 실행하고 종료하는 시작 검사
.\RiceCon.exe --smoke --config "$env:TEMP\controller-smoke\controller.json"
```

새 설치의 기본 목록 파일은 `%LOCALAPPDATA%\RiceCon\controller.json`이다. 기존 설치는 `%LOCALAPPDATA%\RiceController`의 목록과 방송 설정을 계속 사용한다. `--config <파일>`로 다른 목록을 지정할 수 있다. `--smoke`는 창을 숨긴 상태에서 120프레임 실행한다.

개발 도구와 의존성 준비는 [개발용 README](../../README.md)의 다시 빌드 절을 따른다. `Build.ps1`은 컨트롤러도 함께 빌드·검사·설치한다.

```powershell
.\Engine\Build.ps1

# 이미 구성된 이 작업공간의 빌드 디렉터리를 사용하는 경우
cmake --build Engine/Cache/local --config Release --parallel 4
ctest --test-dir Engine/Cache/local -C Release --output-on-failure
cmake --install Engine/Cache/local --config Release --prefix "$PWD"
```

컨트롤러 관련 CTest 대상은 `ControllerModel`, `ControllerWindow`, `ControllerIntegration`, `ControllerStandaloneGame`이다. `ctest --test-dir Engine/Cache/local -C Release -R Controller --output-on-failure`로 해당 검사만 선택할 수 있다. 통합 검사는 별도 복사본에서 플레이어 프로세스와 창을 실제로 생성하며 원본 프로젝트를 수정하지 않는다.

### 제어 지원 빌드와 기존 빌드

RiceCon은 내보낸 게임 실행 파일의 번들 정보를 읽어 제어 지원 여부를 확인한다. 이전 플레이어는 실행 파일 옆의 같은 이름의 `.control` 파일(내용 `1`)로 확인한다.

제어를 지원하는 빌드는 일시정지·숨김·전체화면으로 실행할 수 있다. 제어 기능이 없는 구형 빌드는 제한 모드에서 실행·종료할 수 있다.

## 1. 실행 구조와 범위

- 같은 빌드 파일을 여러 항목에 등록할 수 있다. 각 항목을 재생할 때 독립된 게임 인스턴스가 시작된다.
- 각 프로세스의 게임 루프, 메모리, OpenGL 컨텍스트, 오디오 상태는 독립적으로 유지한다. Windows가 프로세스의 스레드를 여러 CPU 코어에 배치하도록 하며, 코어 고정이나 엔진 내부의 병렬 게임 루프는 추가하지 않는다.
- 한 항목의 중지·실패가 다른 항목에 영향을 주지 않아야 한다. 같은 항목에서 재생을 연타해 중복 프로세스가 생기는 것은 막는다.
- 다중 프로세스 실행은 코어 수에 비례하는 성능이나 무제한 인스턴스를 보장하지 않는다. CPU, GPU, 메모리, 오디오 장치 자원은 공유한다.
- 관리 대상은 내보낸 플레이어 빌드다. 에디터 여러 개의 동시 프로젝트 편집·저장 및 동일 경로로의 동시 Export는 지원 범위에 넣지 않는다.
- 컨트롤러는 별도의 CMake 실행 대상과 자체 ImGui 컨텍스트를 사용한다. 게임 객체·렌더러를 컨트롤러 프로세스에 로드하지 않는다. 기존 Windows/GLFW/OpenGL/ImGui 의존성을 재사용한다.

### 구현 위치

| 기능 | 엔진 연결 | 컨트롤러 구현 |
|---|---|---|
| 독립 플레이어 실행 | `Engine/Sandbox/Source/SandboxApp.cpp`에서 프로젝트를 열고 `Workspace::Play()` 호출 | `Source/ProcessManager.cpp`가 항목마다 프로세스 생성·상태 확인·Job 수명 관리 |
| 프로젝트 위치 지정 | 단독 빌드 파일에 프로젝트와 런타임을 내장 | 이전 플레이어에 한해 별도 프로젝트 경로를 `--project`로 전달 |
| 일시정지·재개 | `Engine/Sandbox/Source/PlayerControl.h`가 메인 루프에서 `Workspace::Pause/Resume()`와 게임 시간 배율을 제어 | 명령 응답 후 실제 상태 반영 |
| 정상 종료 | `Application::Close()`와 창 닫기 이벤트 | 종료 요청 후 프로세스 핸들로 실제 종료 확인 |
| 숨김·전체화면 | 초기 창 가시성 옵션, `PlayerWindowMode`의 GLFW 창 모드 전환 | 시작 모드 전달 및 실행 중 `SetWindowMode` 명령 |
| 자동 실행 검사 | 플레이어 `--smoke --silent-audio`로 120 프레임 실행 후 종료 | 컨트롤러 `--smoke`와 CTest 통합 검사. 일반 재생에는 `--smoke`를 붙이지 않음 |
| 외부 제어 | 플레이어 메인 루프의 `PlayerControl` | `Shared/ControlProtocol.h`의 로컬 named pipe와 JSON 메시지 |

내부 싱글턴은 프로세스별 상태다. 같은 프로세스 안에 `Application`을 여러 개 만드는 방식은 사용하지 않는다. 완성된 Export 프로젝트의 플레이어 다중 실행을 위해 엔진 내부 스레드 구조를 바꿀 필요는 없다.

현재 공유 경로에 대한 제약은 다음과 같다.

- 이미 필요한 에셋 메타데이터가 포함된 완성 빌드를 실행 대상으로 한다. 누락된 `.meta` 생성이나 프로젝트 편집·저장을 여러 프로세스에서 동시에 수행하는 경우는 지원 범위 밖이다. 편집 또는 개별 런타임 파일 쓰기가 필요하면 프로젝트를 항목별로 복제한다.
- 컨트롤러로 실행한 플레이어의 진단 경로는 `Logs/<runId>/functions.tsv`로 분리한다. 제어 인수 없이 독립 실행한 기존 방식은 `Logs/functions.tsv`를 사용한다. 컨트롤러 UI에서 진단 캡처를 예약하는 기능은 제공하지 않는다.
- 에디터의 `EditorLayout.ini`, `EditorSettings.txt` 동시 저장도 플레이어 관리 범위 밖이다.
- 사용자 스크립트가 자체적으로 파일을 출력하면 그 경로도 인스턴스별로 분리해야 한다. 엔진 진단 경로 분리는 임의 스크립트의 출력 위치를 바꾸지 않는다. 동일 빌드를 공유할 때 저장된 프로젝트·에셋은 읽기 대상으로 취급하고 런타임 저장 파일을 덮어쓰지 않는다.

## 2. 메인 화면

상단에 `전체 설정` 메뉴, 그 아래에 `+ 항목 추가` 버튼과 빌드 목록을 배치한다. 목록은 ImGui 테이블로 구성하며 항목이 많아지면 스크롤한다.

```text
RiceCon                                      [−] [□] [×]
전체 설정 ▾
  기본 빌드 폴더 지정 / 방송 설정 / 저장소 설정

[+ 항목 추가]
이름           상태       재생  일시정지  정지  송출  설정  위치  최대화  최소화  제거
빌드 1         실행 중     ▶      II      ■     ●     렌치  파일    □      −      ×
빌드 2         정지         ▶      II      ■     ●     렌치  파일    □      −      ×
```

- `▶`는 초록색 삼각형, 송출 `●`는 빨간색 원으로 그린다. `II`는 세로 막대 두 개, `■`는 정사각형이다. 설정은 렌치, 위치는 파일, 최대화는 창 모양 사각형, 최소화는 가로선이다.
- 그림 문자 폰트에 의존하지 않고 ImGui draw list 또는 포함한 아이콘 자산으로 일정한 크기와 정렬을 유지한다. 각 버튼에 한국어 툴팁을 제공한다.
- 색상과 함께 상태 텍스트 및 비활성 표시를 사용한다. 송출 버튼의 빨간색은 실제 송출 상태를 의미하지 않는다.
- 항목 UI의 식별자는 변경 가능한 이름 대신 `entryId`를 사용한다. Windows의 맑은 고딕으로 한글 이름을 표시·입력한다.
- 제목 표시줄의 컨트롤러 최소화·최대화는 컨트롤러 창에만 적용한다. 항목 안의 최소화·최대화는 해당 빌드에만 적용한다.

## 3. 항목 등록·이름·취소·제거

### 항목 추가

1. **+ 항목 추가**를 누르고 표시할 이름을 지정한다.
2. **실행 파일 선택**에서 내보낸 게임의 `.exe`를 고른다.
3. 기존 플레이어가 별도 프로젝트를 요구하면 **이전 플레이어용 프로젝트 지정**에서 경로를 설정한다.
4. **추가**를 눌러 등록한 뒤 목록의 **재생**을 누른다.

기본 이름은 현재 등록된 이름에 없는 가장 작은 양의 정수 N을 사용한 `빌드 N`이다. `빌드 1`, `빌드 3`이 있으면 다음은 `빌드 2`다. 취소한 추가는 번호를 소비하지 않는다. 삭제·이름 변경 후 비게 된 기본 이름은 다시 사용할 수 있다. 이름 비교는 앞뒤 공백을 제거한 전체 이름으로 하며, `빌드 01`은 `빌드 1`과 별개다.

### 이름과 경로 편집

- 이름을 더블클릭하거나 항목 메뉴의 `이름 변경`으로 편집한다. Enter/확정으로 저장하고 Esc/취소로 원래 이름을 복원한다.
- 이름은 앞뒤 공백을 제거한 1~64자의 표시 문자열로 저장한다. 줄바꿈·제어 문자는 받지 않는다. 사용자 지정 중복 이름은 허용하되 경로 툴팁으로 구분한다.
- 실행 파일·프로젝트 변경은 정지 상태에서만 항목 메뉴의 `경로 변경`으로 수행한다. 변경 취소는 기존 경로를 유지한다. 실행 중인 항목의 이름 변경은 허용한다.
- 등록 이후 파일이 이동·삭제되면 항목을 유지하고 `경로 오류`를 표시한다. 경로 수정 전에는 실행을 막는다.

### 제거

- 항목의 `×` 또는 메뉴의 `항목 제거`는 컨트롤러 등록 정보만 제거한다. 실행 파일과 프로젝트 파일은 삭제하지 않는다.
- 실행 중이면 `중지 후 제거`와 `취소`를 제공한다. 정상 종료가 확인된 뒤 제거한다. 종료 실패 시 항목을 유지한다.
- 추가·편집 취소, 빌드 정지, 항목 제거는 서로 다른 동작으로 표시한다.

## 4. 항목 버튼의 동작

| 버튼 | 정지 상태 | 실행 중 | 일시정지 중 |
|---|---|---|---|
| 초록 `▶` 재생 | 등록된 빌드를 새 프로세스로 시작 | 비활성 | 기존 프로세스를 재개 |
| `II` 일시정지 | 비활성 | 게임 시간·업데이트·오디오를 일시정지 | 비활성 |
| `■` 정지 | 비활성 | 정상 종료 요청 | 정상 종료 요청 |
| 빨간 `●` 송출 | 방송 슬롯 열기 | 방송 슬롯 열기 | 방송 슬롯 열기 |
| 렌치 설정 | 항목별 빈 설정 창 열기 | 동일 | 동일 |
| 파일 위치 | 탐색기에 실행 파일 위치 열기 | 동일 | 동일 |
| 창 `□` 최대화 | 전체화면 모드로 새 프로세스 시작 | 전체화면으로 전환 | 일시정지 상태를 유지하며 전체화면으로 전환 |
| `−` 최소화 | 창을 표시하지 않고 새 프로세스 시작 | 창 숨기기 | 일시정지 상태를 유지하며 창 숨기기 |

`시작 중`·`종료 중`에는 중복 실행과 경합을 일으키는 버튼을 비활성화한다. 시작 중 정지 요청은 시작 취소로 처리해 생성된 자식 프로세스를 회수한다. 프로세스 종료는 실제 종료 신호를 확인한 후 UI에 반영한다.

### 재생·일시정지·정지

- 정지 후 재생하면 저장된 프로젝트의 초기 상태에서 다시 시작한다. 일시정지 후 재생은 동일 PID와 실행 상태를 유지한다.
- 일시정지는 기존 `Workspace::Pause()`에 연결한다. 렌더링, 메시지 처리, IPC는 계속 처리해 정지·재개 명령에 응답한다. 운영체제 수준에서 모든 스레드를 강제 정지하는 방식은 사용하지 않는다.
- 정지는 기존 에디터의 `Workspace::Stop()`만 호출하고 창을 남기는 동작과 구분한다. 컨트롤러의 정지는 플레이어 프로세스를 종료하고 오디오·GPU 자원을 해제한다.
- 정상 종료 요청 후 기본 5초 내에 종료하지 않으면 오류를 표시하고 `강제 종료` 또는 `계속 대기`를 제공한다. 강제 종료는 해당 항목에서 생성해 보유한 프로세스 핸들만 대상으로 한다.

### 최소화·최대화

- 최소화는 실행을 유지한 채 빌드 창을 숨기는 기능이다. 게임 업데이트와 렌더링이 계속될 수 있는 상태를 유지하며, 일시정지나 종료로 취급하지 않는다.
- 숨김 시작은 창 생성 시점부터 적용해 창이 잠깐 나타나는 현상을 막는다. 시작 프로세스의 창 표시 힌트만으로 보장하지 말고 플레이어 창 생성 옵션에 연결한다.
- 최대화는 해당 모니터를 채우는 전체화면 표시다. 기본은 테두리 없는 전체화면이며 모니터의 디스플레이 모드는 바꾸지 않는다. 첫 실행은 기본 모니터, 실행 중 전환은 빌드가 있는 모니터를 사용한다.
- 숨김 상태에서 최대화를 누르면 전체화면으로 다시 나타난다. 전체화면에서 최소화를 누르면 창을 숨긴다. 이 전환은 재시작이나 PID 변경을 일으키지 않는다.
- Esc로 전체화면을 해제하고 이전 창 위치·크기로 복원할 수 있게 한다. 복원 위치가 연결 해제된 모니터에 있으면 기본 모니터 안으로 보정한다.

### 방송 슬롯 설정

1. **방송 슬롯 → + 방송 슬롯 추가 → 게임 선택**에서 등록한 빌드를 배정하고 **게임 실행**을 누른다.
2. **관리 → 방송 설정**에서 YouTube Studio의 RTMPS 서버 URL과 스트림 키를 각각 입력하고 **방송 설정 저장**을 누른다. 스트림 키는 Windows 사용자 계정의 DPAPI로 암호화해 보관한다.
3. 슬롯의 **송출 시작**을 누르면 RiceCon이 실행 중인 게임의 영상과 오디오를 YouTube에 전송한다. 첫 영상 패킷 전송이 확인되면 상태가 `Live`로 바뀐다. 자동 재연결을 켠 슬롯은 송출 중 연결이 끊어지면 설정한 횟수만큼 다시 연결한다.
4. **송출 종료**를 누르면 게임을 계속 실행한 채 해당 슬롯의 송출을 멈춘다. YouTube Studio에서 방송을 공개하거나 종료하는 시점은 해당 방송의 자동 시작·자동 종료 설정을 따른다.

### 항목별 설정 더미

- 렌치 버튼은 `<항목 이름> 설정`이라는 독립 ImGui 창/탭을 연다. 같은 항목에서 다시 누르면 기존 창에 포커스를 준다.
- 본문은 비어 있고 제목 표시줄에 최대화·최소화·닫기 버튼만 둔다. 최대화는 컨트롤러의 작업 영역을 채우고, 최소화는 제목 표시줄로 접고, 닫기는 설정 창만 닫는다. 접힌 제목 표시줄 또는 렌치 버튼으로 복원한다.
- 이 버튼들은 빌드 프로세스의 창 모드나 실행 상태를 변경하지 않는다.
- 방송 프로필과 데이터 편집은 방송 슬롯의 관리 창에서 연다.

### 위치

파일 아이콘은 Windows 파일 탐색기에서 해당 실행 파일이 있는 폴더를 열고 가능하면 파일을 선택한다. 등록되지 않았거나 사라진 경로는 오류 메시지를 표시한다. 경로를 변경하려면 항목 메뉴의 `경로 변경`을 사용한다. 공백·한글 경로를 보존하며 셸 명령 문자열에 원문을 삽입하지 않는다.

## 5. 전체 설정

`전체 설정` 메뉴에서 방송 슬롯으로 이동할 수 있다.

| 메뉴 | 향후 역할 | 현재 상태 |
|---|---|---|
| 기본 빌드 폴더 지정 | 새 항목의 파일 선택 시작 위치 및 빌드 탐색 기준 | 더미 |
| 방송 설정 | 슬롯별 출력·서비스 설정 | 방송 슬롯 탭 열기 |

상단의 기본 빌드 폴더 지정이 더미여도 개별 항목의 실행 파일·프로젝트 선택은 실제로 동작해야 한다.

## 6. 프로세스와 제어 계약

### 프로세스 식별과 수명

- 영속 `entryId`와 실행마다 새로 만드는 `runId`를 분리한다. UI 이름·경로·PID 어느 것도 단독 식별자로 쓰지 않는다.
- 실행 파일 절대 경로, 프로젝트 절대 경로, 작업 디렉터리를 명시해 실행한다. 작업 디렉터리는 기본적으로 실행 파일의 폴더다. 인수는 Windows 규칙에 맞게 인코딩하고 명령 셸을 경유하지 않는다.
- 시작 시 프로세스 핸들, PID, 시작 시각을 보유한다. 창 제목이 동일해도 PID에 속한 대상 창을 찾는다. PID 재사용 때문에 종료 후 옛 PID를 다시 제어하지 않는다.
- UI 스레드에서 프로세스 종료·IPC 응답을 블로킹 대기하지 않는다. 이벤트 또는 짧은 비차단 폴링으로 상태를 수집한다.
- 컨트롤러 종료 시 실행 중 항목이 있으면 `모두 정지 후 종료`와 `취소`를 제시한다. 실행 중 프로세스를 남기고 재접속하는 모드는 제공하지 않는다.
- 컨트롤러 비정상 종료 시에는 자신이 생성한 자식만 정리하는 Windows Job Object 정책을 사용한다. 기존 사용자가 따로 띄운 플레이어는 가져오거나 종료하지 않는다.

### 로컬 IPC 계약

엔진의 기존 메인 루프를 유지하고 실행별 로컬 named pipe 한 개로 제어한다. 새 플레이어는 `--controller-pipe <이름>`, `--instance-id <runId>`, `--window-mode windowed|hidden|fullscreen`을 지원하며 컨트롤러가 인수를 구성한다. `--controller-pipe`와 `--instance-id`는 함께 전달한다. 일반 독립 실행에는 제어 인수가 필요하지 않으며, `--window-mode`만 지정해 숨김 또는 전체화면으로 시작할 수도 있다.

- 컨트롤러가 실행별 고유 파이프를 준비한 후 이름과 `runId`를 플레이어에 전달한다. 로컬 현재 사용자만 접근하도록 제한하고 연결한 PID가 해당 항목에서 실행한 플레이어인지 확인한다. 단일 파일 게임은 그 항목의 Job 안에서 시작된 내장 플레이어의 PID를 확인한다.
- 메시지는 최대 16 KiB의 버전 지정 JSON 레코드다. 기본 필드는 `protocolVersion`, `runId`, `requestId`, `command`, `payload`다. 응답에는 `success`, `state`, `windowMode`, `error`, `gameFrames`, `renderFrames`를 포함한다. `payload`는 `SetWindowMode`에서 모드 문자열을 전달한다.
- 플레이어는 프로젝트와 렌더러 준비 후 `Ready`와 지원 기능 목록을 전송한다. 기본 시작 제한 시간 30초를 넘으면 오류를 표시한다.
- 명령은 `Pause`, `Resume`, `Stop`, `SetWindowMode`, `GetStatus`로 제한한다. 명령 결과에는 같은 `requestId`, 성공 여부, 실제 상태, 오류 설명을 담는다.
- 수신한 상태 변경은 플레이어 메인 루프에서 적용한다. 별도 IPC 스레드를 만들지 않고 메시지 모드 파이프를 비차단으로 처리한다. 프레임당 수신 처리 수와 송신 대기열 크기를 제한한다.
- 일반 명령 응답 제한 시간은 기본 2초다. 응답이 없으면 성공으로 표시하지 않는다. 중복 요청은 `requestId`로 재적용을 막고, 이전 `runId`의 응답은 버린다.
- IPC 연결이 끊겨도 OS의 프로세스 종료 여부를 별도로 확인한다. 살아 있는 프로세스는 `응답 없음`으로 표시하고 정지/강제 종료 경로를 유지한다.
- `.control` 표시 파일이 없는 기존 빌드는 실행·종료 중심의 제한 모드로 표시한다. 기존 빌드는 `Ready` 응답이 없으므로, 프로세스가 살아 있고 그 PID의 GLFW 빌드 창이 생성된 것을 확인하면 `실행 중(제한 모드)`로 표시한다. 이는 게임·씬의 준비 완료를 확인한 상태가 아니다. 오류 대화상자를 GLFW 빌드 창으로 오인하지 않도록 창 클래스도 확인한다. 창 생성 전 종료되거나 기본 30초 내 대상 창을 확인하지 못하면 시작 실패로 처리한다.
- 제한 모드에서는 지원하지 않는 일시정지·숨김·전체화면 제어를 비활성화하고 이유를 툴팁으로 알린다. 성공한 것처럼 표시하지 않는다. 완전한 수용 시험은 제어 계약을 구현한 플레이어를 대상으로 한다.

### 상태 모델

| 상태 | 진입 조건 | 주요 다음 상태 |
|---|---|---|
| 정지 | 등록 직후 또는 정상 종료 확인 | 시작 중 |
| 시작 중 | 프로세스 생성 요청부터 준비 응답까지 | 실행 중 / 종료 중 / 오류 |
| 실행 중 | 준비 완료 또는 재개 응답 | 일시정지 / 종료 중 / 오류 |
| 일시정지 | Pause 성공 응답 | 실행 중 / 종료 중 / 오류 |
| 종료 중 | 정상 종료 또는 시작 취소 요청 | 정지 / 오류 |
| 오류 | 경로 오류, 시작 실패, 비정상 종료, 제한 시간 초과 | 경로 수정·정리 후 정지 또는 다시 시작 |

표시 모드 `windowed`, `hidden`, `fullscreen`은 실행 상태와 별도로 관리한다. 기존 빌드의 시작 완료 기준은 위 제한 모드 규칙을 적용한다. 오류 상태에서도 프로세스가 살아 있는지 따로 보유하며, 이전 실행이 남아 있으면 새 프로세스를 시작하지 않는다. 사용자가 빌드 창을 정상적으로 닫으면 정지, 예상치 못한 실패로 끝나면 종료 코드와 함께 오류를 표시한다.

## 7. 저장 데이터

컨트롤러의 항목 목록은 기본 설정 디렉터리의 `controller.json`에 UTF-8로 저장한다. 임시 파일을 완성한 다음 기존 설정을 교체한다.

```json
{
  "schemaVersion": 1,
  "entries": [
    {
      "entryId": "persistent-uuid",
      "name": "빌드 1",
      "executablePath": "C:/Rice/Builds/Demo.exe",
      "projectPath": "",
      "launchWindowMode": "windowed"
    }
  ]
}
```

- 목록 순서, 이름, 절대 경로, 마지막으로 선택한 시작 표시 모드를 저장한다. 재시작 시 자동으로 빌드를 실행하지 않는다.
- PID, 프로세스 핸들, `runId`, 실행 중 여부는 영속 설정에 저장하지 않는다. 실행별 로그와 IPC 이름은 새 실행에 재사용하지 않는다.
- 손상된 설정은 원본을 보존하고 오류를 표시한다. 검증 없이 임의 실행 파일을 자동 실행하지 않는다.
- 슬롯 설정에는 자격 증명을 가리키는 참조를 저장한다.

## 9. 수용 시험

이 절은 컨트롤러의 수용 조건이다. 조건 목록 자체가 실제 검사 통과 기록을 뜻하지는 않으며, 수행 결과와 검사 한계는 [VALIDATION.md](VALIDATION.md)에 별도로 기록한다.

| 항목 | 통과 조건 |
|---|---|
| 다중 실행 | 동일 실행 파일·동일 샘플 프로젝트로 최소 3개를 동시에 실행해 서로 다른 PID로 유지하고 각 씬이 진행됨 |
| 독립 종료 | 한 항목을 정지해도 나머지의 PID·진행·오디오가 유지됨 |
| 중복 클릭 | 한 항목의 재생을 연타해도 프로세스가 하나만 생성됨 |
| 일시정지 | 선택한 항목의 게임 업데이트와 오디오가 멈추고 렌더·제어 응답은 유지되며 재개 시 같은 PID에서 이어짐 |
| 정지 후 재생 | 정상 종료를 확인한 다음 새 실행으로 초기 씬에서 시작함 |
| 숨김 시작 | 정지 항목에서 최소화를 눌러 창이 나타나지 않고 씬이 진행됨 |
| 전체화면 전환 | 최대화로 전체화면 표시, 최소화로 숨김, 다시 최대화로 복귀하며 PID·실행 상태가 유지됨 |
| 이름 할당 | `빌드 1`, `빌드 3` 존재 시 `빌드 2` 제안. 추가 취소·삭제·이름 변경 후 빈 번호를 재사용함 |
| 취소·제거 | 편집 취소는 원상 복구, 항목 제거는 원본 빌드 파일을 보존, 실행 중 제거 취소는 실행을 유지함 |
| 위치 | 공백·한글 경로의 실행 파일을 탐색기로 표시하고 잘못된 경로에는 명확한 오류를 표시함 |
| 설정 더미 | 항목별 빈 창의 최대화·최소화·닫기가 동작하고 빌드 상태를 바꾸지 않음 |
| 방송 설정 | 빌드의 송출 버튼과 전체 설정의 방송 설정에서 방송 슬롯을 열고 게임을 배정할 수 있음 |
| 상태와 오류 | 빌드 창 수동 닫기, 시작 실패, 강제 종료, 응답 없음이 해당 행에만 반영됨 |
| 영속성 | 컨트롤러 재시작 후 이름·경로·순서가 복구되고 빌드는 자동 시작하지 않음 |
| 공유 파일 | 같은 빌드의 동시 실행에서 프로젝트·에셋 체크섬이 유지되고 실행별 출력이 서로 덮어쓰이지 않음 |
| 종료 정리 | 모두 정지 후 컨트롤러 종료 시 자식 프로세스와 핸들이 남지 않고, 따로 실행한 플레이어는 유지됨 |

검증 기록에는 실행 파일의 해시, 테스트 시각, 인스턴스 수, PID, 시작·종료 코드, 렌더러 정보, 프로젝트 변경 여부를 포함한다. 다중 실행 성공과 코어별 성능 측정은 구분해 기록한다.
